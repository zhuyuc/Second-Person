# 精筛提速（v7 方向 3）决策记录

> 目标：把首步 `context_ms` 从 4-8 秒压到 2-3 秒，降低首字感知延迟。
> 不改架构（精筛仍串行在主对话之前），只压 LLM 精筛本身的耗时。

## 一、诊断：数据实录

用真实 turn 数据（`palace.db::agent_step_metrics`）看首步组成：

| turn | step 1 ctx_ms | step 1 ttft_ms | 用户感知首字 |
|---|---|---|---|
| turn_8b8 | **7678** | 1491 | ~9 秒 |
| turn_7ae | **4060** | 1247 | ~5 秒 |
| turn_8a3 | 282 | 2510 | ~2.8 秒 |

再看 `agent_events` 时间线佐证——`step.started → context.memories` 事件之间的间隔就是 context_ms 的绝大部分：

```
16:44:02  step.started
16:44:09  context.memories   ← 7 秒后才到
16:44:09  context.project
16:44:09  request.header
16:44:14  assistant.tool_calls
```

**结论**：首步 4-8 秒里大部分花在 `retriever.retrieve` 的第 2 层 **LLM 精筛**（`memory/retriever.py::_refine`）。这是一次独立的 LLM API 调用（[app/container.py::llm_refine](../app/container.py)），阻塞主对话前置。

## 二、改动清单

### D1：精筛专属 provider 槽位 `retriever_refine`

**文件**：`infrastructure/provider_registry.py` + `app/container.py`

新增 TaskSlot：

```python
"retriever_refine": TaskSlot(
    key="retriever_refine",
    label="记忆精筛模型",
    desc="每轮首步的记忆检索第 2 层 LLM 精筛...",
    fallback=("agent", "chat"),
    lightweight=True,
),
```

`llm_refine` 优先解析该槽位，未配置时按 fallback 链自动降级到 `agent → chat`。

**运维**：在设置页给此槽位配 haiku / lite / deepseek-lite 等小模型，精筛耗时从 chat 模型的 2-3s 降到 300-800ms。

**兼容**：未配置时行为跟改造前完全一致（走 agent 槽位）。

### D2：候选池硬帽 `CANDIDATE_POOL_HARD_CAP` 20 → 10

**文件**：`memory/_constants.py`

```python
CANDIDATE_POOL_HARD_CAP = 10   # 原 20
```

**依据**：
- hybrid 预筛已经按 BM25 + vector RRF 得分排序
- 尾部（第 11-20 位）与用户 query 的相关性 vs 头部（前 10 位）显著更弱
- 送去精筛主要贡献 input tokens，对最终选出的 top-5 影响很小
- input tokens 减半 → 精筛 latency 减 30-40%

**代价**：真正强指代 + 弱相关记忆场景（正确答案在预筛第 11-20 位）会漏掉，属于长尾。

**回退**：config 覆盖 `candidate_pool_hard_cap` 可以按需调回 20。

### D3：精筛结果 LRU cache

**文件**：`memory/retriever.py`

`Retriever` 类新增 `_refine_cache: OrderedDict`：
- **Key** = `(session_id, query, sorted(candidate_ids) 的 sha1)`
- **Value** = `(chosen_ids, monotonic_ts)`
- **TTL** = 300 秒（`RETRIEVER_REFINE_CACHE_TTL_SECONDS`）
- **Size** = 128 条 LRU（`RETRIEVER_REFINE_CACHE_SIZE`）

**命中场景**：
1. **turn 内异常重试** — 检索超时被 retry，第二次直接命中
2. **用户 regenerate** — 5 分钟内点重新生成，同 query 同候选池
3. **turn_context 缓存失效** — 极少见但存在

**未命中场景**：
- 用户切了新问题（query 变）
- 记忆库有新写入（候选池 id 变）
- 5 分钟窗口外

**关键不变式**：
- **超时/异常时不落 cache**（避免污染）
- Cache 只落成功结果，命中时 `result.degraded = "cache 命中"` 标记
- Cache key 对候选顺序不敏感（sorted）

**内存开销**：128 条 × 平均 5 个 memory_id × 长度 20 字符 ≈ 12KB，可忽略。

## 三、预期收益

按典型场景估算：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 首步 context_ms（首次问） | 4-8s | **1-3s**（小模型精筛 + 10 条 payload） |
| 用户 regenerate（同 query） | 4-8s | **~100ms**（cache 命中） |
| 首字感知延迟（首次问） | 8-9s | **3-4s** |
| 首字感知延迟（regenerate） | 8-9s | **1.5s** |

## 四、未做的事（留待方向 1/2）

- **架构层并行化**（方向 1）：需要处理"首步答复缺记忆"边界情况，暂不做
- **完全移除 LLM 精筛**（方向 2）：需要独立评估 hybrid top-K 相关性、模型自主 memory_search 命中率，属于下一阶段架构决策
- **精筛 provider 慢模型清单**：`slow_model_ids` 已经存在但精筛槽位 `lightweight=True` 只是自动跳过慢模型候选，没有强制小模型；运维配置时手动选小模型即可

## 五、验证与回滚

**验证**：
- 单测：`tests/test_retriever_refine_speedup.py`（10 用例覆盖 pool cap / cache 命中 / TTL / LRU 淘汰 / 失败不落 cache）
- 生产观测：查 `agent_step_metrics.context_ms` 首步中位数应该从 5s+ 降到 2s 以下

**回滚**：三处改动可独立回滚：
- D1：`llm_refine` 改回 `snapshot_for("agent")`
- D2：`CANDIDATE_POOL_HARD_CAP` 改回 20
- D3：`Retriever.__init__` 不初始化 `_refine_cache`，`_refine` 移除 cache 分支

三处都不涉及数据结构或 API 契约变化，纯运行时优化。
