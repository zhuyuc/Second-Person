# 会话上下文管理方案 v2（修订版）

> 基于 v1 方案 + 代码分析报告的完整修订，解决原方案 5 处矛盾、补齐 Langfuse 埋点 / Prompt 注册 / 配置 schema 规划缺口。

---

## 1. 设计原则（修订）

1. **模型上下文窗口是硬边界**——产品明确告知用户，由用户主动切换会话（不再笼统说"1M"，因不同模型窗口各异）
2. **原文永远是原文**——不做任何有损压缩，handoff 摘要是附加产物，不替代原文
3. **会话切换代价通过"一键 + 摘要附件"降到近零**
4. **旧会话永远只读可查**，新会话可主动回查旧会话原文
5. **一切数据以 md 为主副本**，SQLite 仅作派生索引
6. **handoff 摘要与 session 压缩是两套独立系统**——压缩管"会话内 LLM 上下文窗口"，handoff 管"跨会话用户体验连续性"

### 与现有压缩系统的边界

| 维度 | 现有压缩（compression.py） | 本方案 handoff |
| --- | --- | --- |
| 目的 | 控制单会话 LLM 上下文不超窗 | 新会话首条消息注入旧会话脉络 |
| 触发 | 轮次驱动（compression_trigger_rounds） | 用户点击"开启新会话"按钮 |
| 输出 | 六段 JSON（S0-S5），注入 system context | 五段 Markdown，作为附件随首条消息发送 |
| 存储 | `data/sessions/{sid}.md` | `data/artifacts/handoffs/{new_sid}.md` |
| 生命周期 | 随会话压缩迭代覆盖 | 生成后不可编辑，只可整体移除 |

两套系统**并行存在、互不干扰**。达到 95% 阈值时用户切换到新会话，旧会话的压缩系统继续按现有逻辑运行（若旧会话还有人在查看），handoff 摘要是额外生成的跨会话衔接产物。

## 2. 原方案矛盾修正

### 2.1 摘要生成触发时机（修正 §2.3 vs §14.3 矛盾）

**原方案矛盾**：§2.3 说"达到 95% 时同步启动摘要生成"，§14.3 说"关闭视为放弃续期，不生成摘要"——若 95% 时已自动启动，关闭时如何"不生成"？

**修正决策**：**摘要仅在用户点击"开启新会话"按钮时触发，达到 95% 时不自动启动。**

理由：

- 用户达到 95% 后可能选择关闭（§14.3），此时自动生成的摘要成为废弃产物
- 按钮触发保证"生成即有用"，零浪费
- 异步生成不阻塞跳转，用户体验不受影响

修正后流程：

```
达到 95% → 禁用输入 + 显示按钮（不生成摘要）
用户点击按钮 → 创建新会话 → 异步启动摘要生成 → 跳转
用户不点击、直接关闭 → 旧会话保留，无摘要产物
```

### 2.2 阈值动态计算（修正"静态公式 vs 动态注入量"问题）

**原方案问题**：公式中 `system_prompt_tokens + tool_definitions_tokens + L3_memory_injection_tokens` 是动态变化的（SOUL_STYLE 增长、技能注入、记忆注入量波动），静态扣减无法精确覆盖。

**修正决策**：**每轮响应合成后，用 `estimate_tokens()` 实测当前轮实际注入量，计算真实 available_window。**

```python
# 在 response_synthesis 后置阶段计算
actual_injected = estimate_tokens(system_prompt + tools_schema + memory_injection + soul_injection)
available_window = model_context_window - actual_injected - response_reservation(16K)
soft_threshold = int(available_window * 0.90)
hard_threshold = int(available_window * 0.95)
```

每轮响应结束时（`turn_completed` 事件）将阈值信号附加到 SSE 事件中，前端据此更新 UI 状态。

### 2.3 toast 一次性状态持久化（补充原方案遗漏）

**原方案遗漏**："90% toast 全生命周期只弹一次"未定义状态存储位置。

**修正决策**：**状态存储在前端 `sessionStorage`（绑定 session_id），刷新页面后重置但不影响体验。**

理由：

- `localStorage` 持久化过久，需要清理逻辑
- 后端 sessions 表新增字段过度设计
- `sessionStorage` 在标签页关闭时自动清理，标签页内刷新后 toast 可能再弹一次——但刷新本身是低频操作，多弹一次 toast 的用户体验损失可忽略，且刷新后重新计算阈值，弹一次也是合理的提醒

实现：

```javascript
// sessionStorage key 格式
`sp_soft_toast_shown_${sessionId}` = '1'
```

### 2.4 递归回溯深度限制（补充原方案遗漏）

**原方案问题**：§8 说 sess_C 可通过 `view_previous_session` 递归回溯到 sess_A，但未定义深度限制。长链路回溯可能返回大量内容，加剧上下文膨胀。

**修正决策**：**限制递归深度为 2 层（直接前驱 + 前驱的前驱），超出后引导用户手动查看。**

理由：

- 2 层覆盖绝大多数场景（A→B→C 中 C 可回查 B 和 A）
- 更深的链路（D→E→F→G）中 G 回查 D 的需求极低，且摘要链已传递了关键信息
- 工具返回结果注入 LLM 上下文，深度越深返回越多，反而消耗新会话的可用窗口

实现：

- `view_previous_session` 工具内部检查 from_session 链深度，超过 2 层返回提示"更早的会话请手动查看"
- 单次返回结果限制 3000 token（约 2000 中文字）

### 2.5 "1M 上下文"表述修正

**修正**：将"1M 上下文是硬边界"修正为"模型上下文窗口是硬边界"。不同模型的 context_window 各异（如 DeepSeek 128K、GPT-4 128K、Claude 200K），双阈值机制通过动态计算自动适配，无需硬编码。

## 3. 双阈值机制

### 3.1 阈值计算（运行时实测）

在 `agent/core.py` 的 `_pipeline_impl` 后置阶段，调用 `estimate_tokens()` 实测：

```python
# 伪代码：后置阶段阈值计算
actual_injected = estimate_tokens([
    {"role": "system", "content": system_prompt},
    {"role": "system", "content": tools_schema_text},
    {"role": "system", "content": memory_injection_text},
])
response_reservation = 16384  # 16K 固定预留
available_window = (chat_snap.context_window or 128000) - actual_injected - response_reservation
soft_threshold = int(available_window * 0.90)
hard_threshold = int(available_window * 0.95)

# 会话累积 token：从 token_usage 表聚合本会话全部 main_chat 的 input+output
session_total = db.query_one(
    "SELECT COALESCE(SUM(input_tokens+output_tokens),0) t FROM token_usage "
    "WHERE session_id=? AND source='main_chat'", (sid,))["t"]
```

### 3.2 阈值信号 SSE 扩展

`turn_completed` 事件扩展为：

```json
{
  "event": "turn_completed",
  "data": {
    "message_id": 42,
    "threshold": {
      "session_total_tokens": 95000,
      "available_window": 110000,
      "soft_threshold": 99000,
      "hard_threshold": 104500,
      "breached": null
    }
  }
}
```

`breached` 取值：

- `null`：未触达任何阈值
- `"soft"`：达到 90%，需弹 toast
- `"hard"`：达到 95%，需禁用输入

### 3.3 前端阈值处理

```
收到 turn_completed
  → 读取 data.threshold
  → session_total_tokens ≥ soft_threshold 且 sessionStorage 无标记
    → 弹 toast："此会话已接近容量，建议尽快收尾或开启新会话"
    → sessionStorage 写入 sp_soft_toast_shown_{sid}
  → session_total_tokens ≥ hard_threshold
    → 输入框禁用置灰
    → 输入框上方显示「开启新会话」按钮
    → 若之前弹过 toast，自动关闭（hard 优先，不重复提示）
```

### 3.4 前端兜底计算（§14.4 原方案要求）

若前端未收到 `threshold` 字段（后端未升级或 SSE 异常），前端本地兜底：

```javascript
// 已知信息：config 中的 compression_model_window、当前消息列表估算 token
const estimatedTotal = messages.reduce((sum, m) => sum + estimateTokens(m.content), 0)
const fallbackWindow = 100000  // 保守默认值
const softThreshold = fallbackWindow * 0.90
const hardThreshold = fallbackWindow * 0.95
```

## 5. 一键切换流程

### 5.1 完整时序

```
用户点击「开启新会话」按钮
  → POST /api/chat/session/handoff
    → body: { from_session_id: "sess_42" }
  → 后端处理：
    1. 标记旧会话 readonly=1, ended_at=now_cst()
    2. 创建新会话 from_session="sess_42"
    3. 更新旧会话 succeeded_by=新会话ID
    4. 发布 EVT_HANDOFF_GENERATE 事件（异步消费者启动摘要生成）
    5. 返回 { new_session_id: "sess_43", from_session_id: "sess_42" }
  → 前端处理：
    1. 路由跳转到新会话
    2. 输入框上方显示摘要附件组件（状态：generating）
    3. 等待 SSE handoff_ready 事件更新状态
```

### 5.2 首次发送时摘要注入

```
用户在新会话输入第一条消息并发送
  → 前端检查摘要附件状态：
    → ready → 附件路径随消息一起提交
      POST /api/chat/send body: { ..., handoff_path: "artifacts/handoffs/sess_43.md" }
    → generating → 消息暂存到前端内存队列，摘要就绪后自动发送
    → failed → 附件降级为"摘要生成失败"链接，用户可选择：
      a. 不带附件直接发送
      b. 点击链接回旧会话手动整理
```

### 5.3 后端摘要注入（agent/core.py 第一步扩展）

在 `_pipeline_impl` 第 1 步（输入预处理）中，检测 handoff 附件：

## 6. 摘要生成

### 6.1 新增模块 `memory/handoff_summary.py`

```python
class HandoffSummaryGenerator:
    """跨会话 handoff 摘要生成器。"""

    def __init__(self, llm, db, data_dir, tracer):
        self.llm = llm
        self.db = db
        self.data_dir = Path(data_dir)
        self.tracer = tracer

    async def generate(self, from_session_id: str, to_session_id: str) -> Path:
        """生成 handoff 摘要，返回文件路径。失败时生成 status=failed 的占位文件。"""
        ...
```

### 6.2 生成流程

```
1. 读取旧会话全部消息（conversations 表，message_type='normal'）
2. 统计 original_turns、original_tokens
3. 调用 LLM 生成摘要（prompt: agent/prompts/handoff_summary.md）
   - 输入：完整会话历史
   - 输出：五段 Markdown（目标/关键决策/未决问题/进行中思路/侧写与偏好）
4. 检查摘要 token 数
   - ≤ 10K token → 直接写入
   - > 10K token → 二次收敛（prompt: agent/prompts/handoff_converge.md）
     - 输入：首次摘要
     - 输出：压缩到 10K 以内
5. 写入 data/artifacts/handoffs/{to_session_id}.md
6. 更新 sessions.handoff_summary_path
7. 发布 EVT_HANDOFF_READY 事件
```

### 6.3 分段生成（§14.2 旧会话规模异常大）

当旧会话 token 数 > 模型 context_window × 0.6 时：

```
1. 按时间切为 N 段（每段 ≤ budget tokens）
2. 每段独立生成段摘要
3. 合并层：所有段摘要送一次二次收敛，输出 ≤ 10K token
```

### 6.4 失败降级

```
LLM 调用失败 / JSON 修复失败 / 超时（30s）
  → 生成占位文件（status=failed）
  → 正文为固定文案："摘要生成失败，可直接查看完整对话：[旧会话链接]"
  → 更新 sessions.handoff_summary_path
  → 发布 EVT_HANDOFF_READY 事件（前端据此切换附件状态为 failed）
  → Langfuse span 标记 level=ERROR
```

### 6.5 摘要语言规范

- **首段自识别语句**："这是我们在 Second Person 中的上一段对话，共 N 轮。以下是完整脉络。"
- **第一人称视角**：全文使用"我们""我""你"
- **底部原会话引用**：固定一行 `📎 完整对话：{from_session_id}`
- 这些规范写死在 `handoff_summary.md` prompt 中，不依赖代码逻辑

### 7.2 实现逻辑

```python
async def view_previous_session(session_id: str, query: str = None, *,
                                db, data_dir, current_session_from_chain) -> dict:
    # 1. scope 校验：session_id 必须在当前会话的 from_session 链中（≤2 层）
    allowed = _resolve_from_chain(current_session_from_chain, db, max_depth=2)
    if session_id not in allowed:
        return {"error": "只能查看 handoff 链路中的会话，不支持跨越引用"}

    # 2. 检索
    if query:
        # FTS5 全文检索（复用 session_context.search_history）
        results = sessions.search_history(session_id, query, top_k=5)
    else:
        # 返回最近 20 条消息时间线
        results = sessions.get_messages(session_id, limit=20)

    # 3. 结果限制（≤3000 token）
    # ... 截断逻辑

    return {"session_id": session_id, "results": results, "count": len(results)}
```

### 10.2 handoff 路由实现

```python
@router.post("/chat/session/handoff")
async def session_handoff(request: Request):
    body = await read_json_object(request)
    from_sid = body.get("from_session_id")
    c = _c()

    # 1. 校验旧会话存在且未 readonly
    row = c.db.query_one("SELECT readonly FROM sessions WHERE session_id=?", (from_sid,))
    if not row:
        raise HTTPException(404, "会话不存在")
    if row["readonly"]:
        raise HTTPException(409, "会话已结束，不可重复切换")

    # 2. 创建新会话
    new_sid = c.sessions.create_session(from_session=from_sid)

    # 3. 标记旧会话
    now = now_cst().isoformat(timespec="seconds")
    c.db.execute(
        "UPDATE sessions SET readonly=1, ended_at=?, succeeded_by=? WHERE session_id=?",
        (now, new_sid, from_sid))

    # 4. 异步生成摘要
    asyncio.create_task(_generate_handoff(c, from_sid, new_sid))

    return {"new_session_id": new_sid, "from_session_id": from_sid}
```

```javascript
function handleEvent(ev, data) {
    // ... 现有事件处理

    // turn_completed 阈值检测
    if (ev === 'turn_completed') {
        finishStream(data.message_id)
        if (data.threshold) {
            handleThreshold(data.threshold)
        }
    }
    // handoff 摘要就绪
    else if (ev === 'handoff_ready') {
        handoffStatus.value = data.status
        handoffData.value = data
        // 若有暂存消息，自动发送
        if (pendingMessage.value) {
            sendPendingMessage()
        }
    }
}

function handleThreshold(threshold) {
    const { session_total_tokens, soft_threshold, hard_threshold, breached } = threshold
    if (breached === 'hard' || session_total_tokens >= hard_threshold) {
        thresholdBreached.value = 'hard'
    } else if (breached === 'soft' || session_total_tokens >= soft_threshold) {
        if (!softToastShown.value) {
            toast.push('warning', '此会话已接近容量，建议尽快收尾或开启新会话')
            softToastShown.value = true
            sessionStorage.setItem(`sp_soft_toast_shown_${sessStore.currentSid}`, '1')
        }
        thresholdBreached.value = 'soft'
    }
}
```

## 15. 异常处理（修订）

### 15.1 摘要生成超时或失败

- 附件降级显示"摘要生成失败，可直接查看完整对话：[链接]"
- 用户可选择不带附件继续新会话
- Langfuse span 标记 `level=ERROR`，不阻塞用户操作

### 15.2 旧会话规模异常大（> 模型 context_window × 0.6）

- 分段生成：按时间切成 N 段，每段独立摘要
- 合并层走一次二次收敛控制在 10K 内
- 总超时上限 60s，超时降级为 failed

### 15.3 用户在 95% 硬阈值时执意关闭对话

- 关闭视为放弃续期，不生成摘要（因修正后摘要仅在点击按钮时触发，此处无矛盾）
- 侧栏保留旧会话（readonly 未设置）
- 用户下次可通过"从此会话开启新会话"手动触发

### 15.4 前端未收到 gateway 阈值字段

- 前端本地兜底计算（基于消息列表 token 估算 + 保守默认窗口 100K）
- 保证阈值 UI 状态可用，不依赖单次响应

### 15.5 view_previous_session 检索返回空

- LLM 回复"上一会话中未找到该主题的直接讨论"
- 提示用户可主动打开旧会话查看，或提供更多关键词
- 不虚构内容

### 15.6 新会话首条消息发送时摘要仍在生成

- 消息暂存到前端内存队列（`pendingMessage` ref）
- `handoff_ready` SSE 事件到达后自动发送
- 若用户切换会话或刷新页面，暂存消息丢失（可接受：用户重新输入即可）

## 19. 多次切换链路（修订）

```
sess_A → sess_B → sess_C

sess_C:
  - 附件只带 sess_B 的摘要（直接前驱）
  - view_previous_session 可查 sess_B（1 层）和 sess_A（2 层）
  - sess_B 的 metadata: from_session=sess_A
  - sess_A 的 metadata: succeeded_by=sess_B

超过 2 层时：
  - 工具返回提示："更早的会话请从侧栏手动查看"
  - 不虚构、不猜测
```

每层只承担一层的摘要成本，链路无限延展但单层开销恒定。
