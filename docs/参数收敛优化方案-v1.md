## 0. 背景与判定原则

### 问题
`SettingsView.vue` "参数"页展示 60 个参数，其中大量是**内部实现细节**（权重系数、相似度阈值、RRF 平滑参数、意图分类降权），用户看不懂也不该拧；另有伪开关（`memory_sensitive_scan_enabled` 让用户关掉隐私保护）跟之前批评的 `llm_available` 是同一物种。

### 判定原则
一个参数应该出现在设置页里，当且仅当：
1. **用户能理解**：不需要读代码就能知道拧了会发生什么
2. **拧了不会破坏系统一致性承诺**：不会让某个契约（安全、幂等、去重）失效
3. **有真实使用场景**：有用户合理会想改的情境（比如冷启动/成本敏感/隐私偏好）

不满足 1 → **收敛为内部常量**（`memory/_constants.py` 或就地硬编码）
不满足 2 → **删掉**（安全兜底不给开关）
不满足 3 → **收敛为内部常量**
多个概念重复表达 → **合并为一个语义化参数**

### 三种改动动作
- **删（DELETE）**：从 `PARAM_SCHEMA` 移除；`config.yaml` 存量值由 `load()` 的孤儿清理自动清除；代码里 `config.get(key, default)` 的 `default` 变成硬编码常量或抽到 `_constants.py`
- **收敛（INTERNAL）**：从 `PARAM_SCHEMA` 移除，但在 `memory/_constants.py` 保留可读的常量声明；调用点从 `config.get()` 改为 `import _constants`
- **合并（MERGE）**：多个 key → 一个语义化 key；调用点各自按倍数/映射派生

### H. 废除意图分流（**最重要**）

**风险等级：🟠 中高** —— 涉及 retriever 5 处、观测字段、诊断契约。

这是 A~H 里**最能体现"删开关而非留分叉"精神**的一个改动。它跟之前的 RT-1..RT-5 是同一物种，只是收尾。

#### 现状
- `memory/retriever.py:51-65` 有 `classify_query()` / `has_recall_intent()` / `is_continuation()` 三个正则分类器
- `memory/retriever.py:184-185` 两个降权系数 `pk_factor` / `km_factor` 依赖 `classify_query()` 结果
- `memory/retriever.py:376/394` 诊断字段 `query_type` 也写这个
- `retrieval_events` 表存 `query_type`

#### 判定
"个人问题 vs 知识问题"这个二分本身就是脆弱启发式。用户问"我常用 pandas 做数据分析" —— 是个人问题（"我"）还是知识问题（"pandas"）？分类器给一个答案，权重就翻一次；用户改一个字（"帮我看看 pandas 的用法" vs "介绍 pandas"）分类就翻转，检索结果肉眼可见地变——**这是不该有的行为分叉**。

正确做法：**LLM 精筛已经能看到 source_type=memory/knowledge 标签，让它自己决定用哪一类**。

#### 删除
- `personal_query_knowledge_factor`（config）
- `knowledge_query_memory_factor`（config）
- `classify_query()` 函数
- 诊断字段 `query_type`（并从 `retrieval_events.query_type` 停止写入，但列保留供历史查询）

#### 保留但收敛
- `has_recall_intent()` 保留（仍用于低阈值 fallback 重跑）—— 这是"用户明确要求回忆时放宽阈值"的合理触发，不是行为分叉

#### 改动清单
1. `memory/retriever.py`：

### I. 决策：`tool_projection_enabled` 存废

**风险等级：🔴 高** —— 影响每轮工具集大小与 token 消耗，需要业务评估。

#### 现状
- `agent/prompt_assembler.py:74`：`if not self.config.get("tool_projection_enabled", True): 返回全部工具`
- `agent/turn_runtime.py:184`：`tools = self._project_tools(message, step)`
- `agent/turn_runtime.py:355`：`_project_tools` 定义

行为分叉：
- `True`（默认）：根据 message 意图动态挑选可能用到的工具子集 → 省 token
- `False`：始终注入全部工具 → 更全但 token 高

#### 判定：是否是"跟 llm_available 同类的伪开关"？
- **不是**。这个开关有真实成本影响（token）
- **但**：默认 True 的时候，"选择要不要投影"的意图判定本身就是启发式，跟之前批评的 `classify_query` 逻辑相似
- 真正正确的做法：**始终注入所有工具**（现代 LLM 有能力从大工具集中选择），把这个开关删掉

#### 需要的评估
在做删除决定之前，需要评估：
- 项目当前有多少工具？→ grep `register_tool` 数一下
- 每个工具的 schema 有多大 token？
- 全量注入 vs 按需投影的 token 差是多少？
- 是否值得为了这个 token 差保留脆弱的意图分流？

**这个决策不在方案定稿范围内**，需要单独评估后决定是否列入下一版方案。
