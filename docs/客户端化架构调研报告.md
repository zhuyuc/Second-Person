# Second Person 客户端化架构调研报告

> 调研日期：2026-09-01
>
> 目标：将当前本地 Web 应用演进为可安装、可更新、具备基础编程能力的跨平台桌面客户端。

## 1. 结论摘要

建议采用 **Tauri 2 + Vue 3 作为桌面壳，保留 Python Agent 内核作为 sidecar，逐步引入本地 app-server 协议** 的路线。

这不是一次性重写。当前项目已经具备相对完整的 Agent、记忆、工具、项目和多渠道能力，最有价值的做法是先解决安装、进程生命周期、权限和协议边界，再决定哪些热点模块值得迁移到 Rust。推荐目标如下：

```text
桌面窗口（Tauri 2 / Rust）
        │ 受限 IPC、窗口、托盘、更新、凭据
        ▼
Vue 3 客户端（现有 frontend）
        │ 版本化 Client API
        ▼
本地 App Server（阶段一：FastAPI；阶段二：JSON-RPC）
        │
        ├─ Agent Core / TurnRuntime（Python，保留）
        ├─ Tool Runtime：文件、补丁、终端、Git、Web、MCP
        ├─ Memory：Markdown 主副本 + SQLite/FTS5/向量索引
        ├─ Scheduler / Connectors / Plugins
        └─ 可选 Embedding sidecar
```

核心判断：

1. **短期不要重写 Agent 内核。** Python 代码量和业务覆盖面已经较大，直接改 Rust 或 TypeScript 会把产品风险集中到一次迁移中。
2. **桌面化的关键不是换 UI，而是建立客户端与宿主之间的稳定协议。** Codex 的 app-server、DeepSeek Harness 的 Host/Client 拆分都说明了这一点。
3. **编程能力必须作为一等能力设计。** 文件、补丁、终端、测试、Git、任务取消、审批和沙箱需要统一的事件模型，不能继续只靠若干普通 HTTP 路由拼接。
4. **安全默认值要提高。** 当前文档明确允许本地工具直接执行且没有审批环节；桌面客户端面向真实项目目录时，应默认只读或工作区可写，并对写文件、执行命令、联网和插件安装提供可审计的授权。

## 2. 范围与假设

本报告按以下目标理解“改成客户端”：

- 首发平台为 Windows，同时支持 macOS、Linux；后续可评估移动端，但不把移动端约束带入第一阶段。
- 用户安装一个桌面程序即可启动，不要求预装 Python、Node、数据库或 Docker。
- 数据优先本地保存，模型可以是远程 API，也可以是本地模型服务。
- 单用户优先，但未来可能通过 Gateway/远程客户端访问同一个运行实例。
- 客户端需要完成基础代码工作，而不是只展示聊天：能理解项目、修改文件、运行命令、执行测试并展示变更。

如果产品实际只需要“本机浏览器快捷方式”，现有 FastAPI + Vue 已经足够；下文的客户端化方案针对真正的可安装桌面应用。

## 3. 当前项目盘点

### 3.1 已有能力

| 领域 | 当前实现 | 对客户端化的价值 |
| --- | --- | --- |
| UI | Vue 3 + Vite，构建到 `app/static` | 可直接复用为桌面渲染层 |
| 宿主 | FastAPI + Uvicorn，`start.py` 负责启动和端口 | 可作为过渡 App Server；需要去除端口依赖或收敛为本地协议 |
| Agent | `AgentCore`、`TurnRuntime`、事件化步骤、流式 SSE、取消 | 已接近 coding-agent 的执行骨架 |
| 工具 | 文件读写、shell、Web、文档导出、MCP | 基础编程能力的大部分后端已存在 |
| 工作区 | 项目、工作区解析、三档 sandbox policy | 可扩展为客户端授权和项目选择流程 |
| 记忆 | Markdown 主副本、SQLite、FTS5、向量检索、恢复和备份 | 适合 local-first，数据迁移成本较低 |
| 扩展 | Provider、MCP、插件、IM Gateway | 适合抽象成 Host/Client/Plugin 三类边界 |
| 可观测性 | Langfuse、trace、事件和工具摘要 | 可保留；客户端增加本地诊断导出 |
| 启动 | 单实例、动态端口、子进程监督、Embedding 服务 | 能力齐全，但与桌面生命周期和更新机制还未统一 |

### 3.2 主要改造缺口

当前后端 Python 业务约 2.56 万行，前端源码约 1.93 万行（按仓库文件统计，未计入构建产物）。这使得全量迁移到 Rust 或 TypeScript 不是一次普通的“换壳”，而是需要长期并行验证的产品重写。

1. **运行时依赖重。** Python 主环境、Embedding 独立虚拟环境、模型文件和可选 IM SDK 不适合直接暴露给终端用户。
2. **API 面向浏览器。** SSE 和 localhost 端口适合现有 Web UI，但桌面端需要连接握手、版本协商、断线恢复、权限请求和结构化二进制/文本流。
3. **权限模型不完整。** 当前路径围栏和命令黑名单是有价值的起点，但“黑名单 + danger-full-access”不能作为代码执行产品的最终策略。
4. **前后端契约容易漂移。** 目前主要依赖手写 JSON 和 SSE 事件注册；客户端、Python 宿主和未来 Rust 组件需要共享或生成类型。
5. **插件生命周期不统一。** Python 插件、MCP 子进程、IM 适配器和 Embedding 进程需要由一个桌面 Supervisor 统一启动、停止、升级和诊断。
6. **缺少桌面发布链路。** 需要安装包、代码签名、自动更新、迁移、崩溃报告、日志导出和跨平台构建矩阵。

## 4. 参考项目调研

### 4.1 OpenAI Codex

Codex 当前维护的 CLI 实现以 Rust 为主，仓库将业务逻辑放在 `core`，并将 TUI、exec、CLI 等界面分开；官方说明明确希望 `core` 最终成为可复用库。其 `app-server` 使用双向 JSON-RPC，支持 stdio、WebSocket 和 Unix socket，面向 Thread、Turn、Item 三层交互原语，并通过通知流输出进度、工具和审批事件。[Codex Rust README](https://github.com/openai/codex/blob/main/codex-rs/README.md) · [app-server README](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) · [core README](https://github.com/openai/codex/blob/main/codex-rs/core/README.md)

值得借鉴的不是“全部改 Rust”，而是以下边界：

- 核心执行逻辑与 UI 解耦，同一套核心可以被 TUI、CLI、IDE 或桌面 UI 驱动。
- 协议是双向的：客户端既接收事件，也能响应审批、用户输入和取消请求。
- 线程、轮次和项目项有持久身份，UI 可以恢复、分支、读取和重放。
- 外部传输使用 JSON-RPC，进程内可使用类型化通道；队列有界，消费跟不上时显式返回过载而不是无限积压。
- 文件/命令执行有独立的 exec-server 和平台沙箱，不把所有宿主权限直接暴露给渲染层。

对 Second Person 的启示：把 `turn_id`、`step`、`tool_call`、`file_change`、`approval` 和 `artifact` 统一成可恢复事件，并先定义一个独立的本地协议。

### 4.2 DeepSeek Harness

DeepSeek Harness（`dsh`）采用“一切皆插件”，由 Cordis 驱动；模型、工具、技能、会话、存储、循环、调度和 UI 都可以替换。官方架构文档把事件分为可持久化的 session events、运行中的 agent events 和能力扩展事件，并要求模型可见输入都能从会话日志重建。[项目 README](https://github.com/deepseek-ai/deepseek-harness) · [架构文档](https://deepseek-harness.github.io/deepseek-harness/en/reference/) · [三角色能力设计](https://deepseek-harness.github.io/deepseek-harness/en/develop/practice/)

当前实现是 Node.js/TypeScript monorepo，要求 Node 22 系列，使用 pnpm workspaces，同时存在 `packages/host` 与 `packages/client` 的类型和构建边界。Web UI 通过本地 Web Server 启动，插件可贡献客户端模块和会话渲染节点。[package.json](https://raw.githubusercontent.com/deepseek-ai/deepseek-harness/master/package.json) · [客户端模块](https://deepseek-harness.github.io/deepseek-harness/reference/subsystems/client-modules)

值得借鉴的设计：

- **能力接缝（capability seam）**：定义、实现、消费三者分离；例如 shell 定义、local provider、模型工具分别演进。
- **事件日志优先**：会话历史、UI 重放、分支和恢复都从 durable events 派生，不由前端猜测状态。
- **Host/Client 分离**：浏览器客户端只消费宿主投影，不直接折叠全部原始事件，也不持有宿主权限。
- **插件可卸载**：注册监听、工具和定时器具有生命周期，避免扩展带来全局泄漏。

需要谨慎的地方：该项目仍处于开发者预览，官方明确提示存在破坏性变更；Second Person 可以吸收事件和插件思想，但不应把核心产品直接绑定到其内部 API。

### 4.3 OpenClaw

OpenClaw 是 TypeScript/Node.js 的多渠道个人助手。其核心是本地 Gateway，负责会话、工具、事件和渠道连接；Control UI、CLI、TUI、消息渠道以及设备节点都连接到 Gateway，工具、技能和插件负责扩展能力。[OpenClaw README](https://github.com/openclaw/openclaw) · [package.json](https://raw.githubusercontent.com/openclaw/openclaw/main/package.json)

官方架构强调“trusted gateway、untrusted execution、deterministic policy”：入站消息按不可信输入处理，主会话工具默认在宿主运行，跨用户或远程暴露时应配置配对、沙箱和安全策略。[OpenClaw README 安全章节](https://github.com/openclaw/openclaw#security)

值得借鉴的设计：

- 一个本地控制平面统一 UI、CLI、IM 和设备节点，避免每个入口都实现一套 Agent 状态机。
- 个人模式和共享 Gateway 通过配置区分，便于未来从单用户客户端扩展到远程工作站。
- 渠道适配器、技能和插件都围绕稳定的 Gateway 契约接入。

与本项目的差异：OpenClaw 从 Node 生态出发，适合把客户端和 Gateway 一起 TypeScript 化；Second Person 现有核心是 Python，直接照搬会造成大规模迁移。

## 5. 语言与框架选型

### 5.1 候选方案

| 方案 | 语言/框架 | 优点 | 主要代价 | 结论 |
| --- | --- | --- | --- | --- |
| A | Tauri 2 + Vue 3 + Python sidecar | 复用现有 UI 和内核；安装包小；Rust 适合窗口、进程、权限和更新 | 需要维护 Rust 与 Python 两个运行时；sidecar 调试和签名有成本 | **首选，分阶段落地** |
| B | Electron + Vue/React + Node Gateway | Node 生态成熟，接近 DeepSeek Harness/OpenClaw；IPC 和插件资料多 | Chromium/Node 体积和内存较大；必须严格隔离 renderer；仍要保留 Python 或重写内核 | 可作为团队偏 TypeScript 时的备选 |
| C | Rust 原生核心 + Tauri UI | 单一原生运行时，性能、沙箱、分发和长期维护最好，接近 Codex | Agent、记忆、文档解析和 Provider 几乎需要重写；首期周期长、风险高 | 第二阶段以后按模块迁移 |
| D | PySide6/Qt | Python 内核可直接调用；桌面控件完整 | 现有 Vue UI 要重写；前端生态和复用价值损失；打包体积不一定更小 | 不推荐 |

Tauri 官方架构是 Rust 后端与系统 WebView 通过消息传递连接，使用系统 WebView 可以显著降低安装体积；它适合把桌面能力收敛在 Rust，而不让前端拥有文件系统和进程权限。[Tauri Architecture](https://tauri.app/concept/architecture/)

Electron 也可以满足需求，但必须启用 context isolation、关闭 renderer 的 Node integration、限制导航和外部窗口，并通过受限的 `contextBridge` 暴露 API；官方安全文档把这些列为基本要求。[Electron Process Model](https://github.com/electron/electron/blob/main/docs/tutorial/process-model.md) · [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)

### 5.2 推荐语言分工

| 层 | 推荐语言 | 原因 |
| --- | --- | --- |
| 桌面壳、进程生命周期、原生权限、更新 | Rust | 内存安全、跨平台原生能力、适合 Supervisor 和受限 IPC |
| UI | TypeScript + Vue 3 | 现有代码可复用；补齐类型和客户端状态模型 |
| Agent、记忆、文档解析、Provider | Python（第一阶段） | 现有资产最大，迭代速度快，避免业务重写 |
| 协议 schema | JSON Schema + 生成 TypeScript/Python 类型 | 让 Host、Client、测试和插件共享契约 |
| 插件/外部工具 | MCP/JSON-RPC；必要时 Python/Node 独立进程 | 进程隔离，避免插件污染主进程 |
| 高风险执行器（后续） | Rust | 沙箱、PTY、进程树、超时、资源限制更适合原生实现 |

Python sidecar 可以使用 PyInstaller 打包；官方文档要求分别在每个目标操作系统构建，建议先验证 one-folder，再评估 one-file。[PyInstaller Usage](https://pyinstaller.org/en/stable/usage.html)

### 5.3 决策矩阵

评分为 1-5 分，分数越高越适合本项目；权重按“先交付可用客户端，再逐步提高原生能力”的目标设置。分数是基于当前仓库复用程度、目标功能和团队需要承担的迁移量做出的工程判断，不是框架厂商指标。

| 评估项 | 权重 | Tauri + Python sidecar | Electron + Node/TS | 全量 Rust 重写 | PySide6/Qt |
| --- | ---: | ---: | ---: | ---: | ---: |
| 现有代码复用 | 25% | 5 | 3 | 1 | 4 |
| 首版交付速度 | 20% | 4 | 3 | 1 | 2 |
| 安装包与资源占用 | 15% | 4 | 2 | 5 | 3 |
| 本地执行安全边界 | 15% | 4 | 3 | 5 | 2 |
| 插件/协议扩展 | 10% | 4 | 5 | 4 | 2 |
| 跨平台发布 | 10% | 4 | 4 | 4 | 3 |
| 长期统一运行时 | 5% | 2 | 4 | 5 | 3 |
| **加权结果（5 分制）** | **100%** | **4.05** | **3.20** | **2.85** | **2.85** |

因此推荐顺序是：先落地 Tauri + Python sidecar；当协议和安全边界稳定后，再按 profiling 结果把执行器等模块迁移到 Rust；只有当团队明确愿意承担大规模业务重写时，才考虑全量 Rust 或全量 Node/TypeScript。

### 5.4 长期维护复核：它不是终局最优

上一版结论需要区分两个问题：

| 问题 | 最优答案 |
| --- | --- |
| 现在如何以最小风险做出可安装客户端 | Tauri 2 + Vue 3 + Python sidecar |
| 五年以上如何降低运行时、权限和发布复杂度 | Tauri 2 + Vue 3 + Rust Host/执行器 + Python 独立工作进程 |

如果把“长期维护”放到第一优先级，`Tauri + Python sidecar` 有四项持续成本：

1. **三套运行时税。** Rust 负责桌面、TypeScript 负责 UI、Python 负责业务；每个跨层功能都要维护类型、日志、错误、取消和版本映射。
2. **sidecar 发布税。** Python 二进制需要在每个 OS/架构分别构建、签名和回归；Tauri sidecar 也要求按 target triple 提供产物。Tauri 官方确实支持任意语言的 sidecar，但这解决的是集成问题，不是长期运维问题。[Tauri Sidecar](https://v2.tauri.app/develop/sidecar/)
3. **权限边界重复。** Tauri capability、Python 路径策略、shell 黑名单和 MCP 权限可能出现“宿主允许、业务拒绝”或相反的漂移，安全审计要覆盖多个实现。
4. **故障面扩大。** 桌面壳、Python server、Embedding worker、MCP 子进程和本地数据库各自可能重启；如果没有严格的事件和 Supervisor 契约，问题会表现为“窗口还在但任务已丢失”。

因此，Python sidecar 应被视为**迁移期实现**，而不是让 UI 永久依赖 FastAPI/Python 内部对象。长期目标应是：

- 协议、事件日志、数据格式和插件边界保持语言无关；
- Rust 逐步接管拥有宿主权限的 Host、process/PTY、文件策略、Git 和更新；
- Python 保留在 LLM/Embedding/文档解析等适合快速迭代或已有生态的工作进程中；
- UI 只依赖版本化 Client API，不感知 Python 类、FastAPI 路由或 sidecar 端口。

这个目标比“全量 Rust 重写”更务实，也比“Python sidecar 永久化”更容易维护。是否继续迁移 Agent loop，要由真实数据决定，而不是在项目开始时预先承诺。

长期目标的主观评分如下（仍为 1-5 分，仅用于比较方向）：

| 候选长期形态 | 运行时统一 | 宿主安全 | 迁移风险 | 插件/UI 扩展 | 综合判断 |
| --- | ---: | ---: | ---: | ---: | --- |
| Tauri + Python sidecar 永久化 | 2 | 3 | 5 | 4 | 可交付，但维护税最高 |
| **Tauri + Rust Host/执行器 + Python workers** | **4** | **5** | **3** | **4** | **推荐终局方向** |
| Tauri + 全量 Rust | 5 | 5 | 1 | 4 | 只有团队和预算充足时考虑 |
| Electron + Node/TS Gateway + Python | 3 | 3 | 3 | 5 | 生态强，但资源和安全边界较重 |

结论是：**当前方案是最优的迁移起点，不是无条件最优的终局架构。** 现在应投资协议和事件模型，为以后保留 Rust 化路径，而不是把 Python sidecar 的内部 API 固化成产品接口。

### 5.5 按产品目标选择，而不是按框架偏好选择

| 产品优先级 | 更合适的选择 | 说明 |
| --- | --- | --- |
| 3 个月内交付可安装客户端，团队 Python/Vue 为主 | Tauri + Python sidecar | 复用最多，接受过渡期双运行时 |
| 5 年以上维护、代码执行安全和多种客户端 | Tauri + Rust Host/执行器 + Python workers | 高权限路径收敛，协议和事件日志稳定 |
| 以插件生态和 TypeScript 招聘/协作效率为首要目标 | Electron 或 Tauri + TypeScript Gateway + Python workers | 牺牲部分资源占用，换取统一 JS/TS 扩展体验 |
| 只需要本机使用，不需要系统托盘/安装/原生能力 | 继续维护 FastAPI + Vue Web | 不为“客户端”承担不必要的桌面复杂度 |

所以，对当前项目的审慎结论是：**推荐方案在现阶段仍然合理，但准确名称应是“协议先行的渐进式客户端化”，而不是“Python sidecar 终局方案”。**

## 6. 推荐目标架构

### 6.1 进程拓扑

```text
┌──────────────────────────────────────────────┐
│ Tauri Host (Rust)                            │
│ - 单实例 / 托盘 / 更新 / 日志 / 凭据         │
│ - 启停与监控 sidecar                         │
│ - IPC allowlist + capability scopes          │
└───────────────┬──────────────────────────────┘
                │ local IPC（优先 stdio/UDS）
┌───────────────▼──────────────────────────────┐
│ Python App Server                            │
│ - 协议握手、版本、请求路由、事件回放          │
│ - AgentCore / TurnRuntime                     │
│ - ToolExecutor / Memory / Projects            │
└───────┬───────────────────┬──────────────────┘
        │                   │
  Embedding worker     MCP / shell / LSP workers
        │                   │
        └──────────── local data dir ───────────┘
              Markdown + SQLite + logs + exports
```

第一阶段可以让 Tauri 启动 Python FastAPI 并连接随机 loopback 端口，以最小改动复用现有 API；第二阶段将客户端需要的能力迁移到版本化 JSON-RPC，HTTP/SSE 作为兼容适配层保留；第三阶段再把进程执行和安全边界下沉到 Rust。

### 6.2 协议建议

采用 `initialize -> session/* -> turn/* -> event/* -> approval/*` 的双向协议，设计上参考 Codex app-server，但字段归属以 Second Person 现有契约为准。

最小对象：

- `Session`：会话、项目、工作区和 sandbox policy。
- `Turn`：一次用户输入到终态的执行。
- `Step`：一次模型请求及其工具调用。
- `Item`：用户消息、模型消息、工具调用、工具结果、文件变更、命令输出、审批和产物。
- `Event`：追加到事实日志的持久事件，客户端从事件重建视图。
- `Job`：后台索引、Embedding、测试或文档导出任务。

必须具备：

1. 连接握手和协议版本；客户端能力声明（是否支持审批、图形、PTY、断点续传）。
2. `request_id`、`session_id`、`turn_id`、`step_id` 全链路关联。
3. 有界事件队列和明确的过载错误；客户端落后时可从事件序号继续读取。
4. 终态幂等：`turn_completed`、`cancelled`、`failed` 只能有一个最终状态。
5. 服务端发起的请求：审批、用户补充信息、选择工作区、登录 Provider。
6. schema 生成和兼容测试，未知事件字段必须可忽略。

现有 SSE 事件不必立即删除，可定义 `SseTransportAdapter` 将其映射为同一套事件对象，避免前后端同时重写。

### 6.3 插件和能力接缝

借鉴 DeepSeek Harness 的三角色模型，每个可替换能力拆成：

```text
Definition（接口与 schema）
      ↓
Provider（本地、远程或平台实现）
      ↓
Consumer（Agent tool、UI、后台任务或 Gateway）
```

优先拆分的能力：

- `llm`：Provider、流式输出、token 计量和模型能力目录。
- `workspace`：项目路径、读取/写入权限、忽略规则和 Git 根。
- `process`：命令、PTY、进程树、超时和资源限制。
- `session-store`：SQLite/文件日志、恢复、分支和压缩。
- `memory`：Markdown 文件、索引、Embedding 和治理。
- `channel`：Web UI、桌面通知、IM 连接器。

插件默认采用独立进程 JSON-RPC/MCP；只有受信任、版本锁定且不需要高权限的 UI 插件才进入客户端 bundle。插件 manifest 应声明版本、权限、入口、依赖、数据目录和卸载清理动作。

## 7. 基础编程能力规格

客户端首个可用版本至少应覆盖以下闭环：选择项目 → 分析代码 → 修改 → 执行验证 → 查看差异 → 接受或撤销。

### 7.1 工作区与上下文

- 选择一个或多个项目根目录，保存项目 ID 与显示名。
- 识别 Git 根、`.gitignore`、项目说明文件（如 `AGENTS.md`、`README`）。
- 文件树、文件名/内容搜索、按行读取，限制单次返回大小。
- 将选中目录、文件、搜索结果作为显式上下文附件，而不是把整个项目塞进提示词。
- 记住每个项目的模型、工具和 sandbox policy。

### 7.2 文件和补丁

- `read`、`write`、`list`、`search`、`apply_patch` 五类基础操作。
- 写入前生成统一 diff；支持预览、接受、拒绝和撤销。
- 原子写入、并发修改检测、编码识别、超大文件截断提示。
- 所有路径先 canonicalize，再检查工作区和白名单；拒绝符号链接逃逸。

### 7.3 终端与验证

- 一次命令一个 `command_id`，实时输出、退出码、耗时和工作目录可见。
- 支持取消、超时、进程树终止和后台任务；需要 PTY 时再分配 PTY。
- 提供“运行测试/构建/格式化”的结构化快捷动作，同时保留普通 shell。
- 解析 JUnit、pytest、Vitest 等常见结果，至少能标记通过、失败、跳过和错误位置。
- 记录环境摘要（OS、解释器、包管理器、Git commit），不把密钥写入事件日志。

### 7.4 Git 和交付

- 展示 status、diff、分支和最近提交；Agent 默认不自动 commit/push。
- 支持按文件或补丁粒度接受变更。
- 生成可下载的补丁、报告和文档产物。
- 任务完成时给出验证证据，而不是只说“已完成”。

### 7.5 Agent 交互

- 计划、当前步骤、工具状态、命令输出、文件 diff 和最终结论分栏展示。
- 支持停止、继续、重试、重生、从某一事件分支。
- 审批请求可在 UI、系统通知和 CLI 入口统一处理。
- 断线后按事件序号恢复，不能依赖浏览器内存中的临时状态。

## 8. 安全设计

### 8.1 默认策略

建议将客户端默认档位调整为：

| 操作 | 默认行为 |
| --- | --- |
| 读取项目文件 | 允许，但仅限已选择的工作区 |
| 写文件/应用补丁 | 首次或跨根目录时请求批准；可设置项目级信任 |
| 执行 shell | 默认请求批准；只允许项目工作目录和受控环境 |
| 联网/Web/MCP | 按工具和域名授予权限，默认不把密钥暴露给模型 |
| 安装插件/依赖 | 显式批准，展示来源、版本和权限 |
| 提交/推送 Git | 永远显式确认 |
| `danger-full-access` | 隐藏在高级设置，显示风险并记录审计事件 |

### 8.2 对现有实现的针对性改造

- `tools/sandbox.py` 的高危命令正则可以保留为快速拒绝层，但不能替代命令解析、权限策略和审批。
- `PolicyStore` 已有三档模型，应增加“本轮临时授权”和“工具能力声明”，并把策略变更写入事件流。
- `app/main.py` 当前 localhost 服务适合过渡，但桌面端应使用随机会话令牌或 UDS/stdio，避免本机其他进程直接调用全部 API。
- Provider 和 MCP 凭据必须只在 Rust/宿主或 Python server 的安全存储中使用，渲染层只拿到脱敏状态。
- 远程或 IM 入站消息必须按不可信输入处理；不要因为是单用户模式就跳过来源、渠道和工具权限检查。
- 所有工具输出继续经过凭证脱敏、注入检测和大小限制；把命令原文、参数和结果摘要写入可导出的审计日志。

## 9. 打包、更新与数据迁移

### 9.1 安装包

- Tauri bundle 负责桌面安装包、快捷方式、托盘和卸载。
- Python 主服务用 PyInstaller 在 Windows/macOS/Linux 分别构建；不要在用户机器上现场创建 venv。
- Embedding 模型和大型运行时作为可选组件，首次使用时下载并校验 SHA-256；无模型时保留 FTS5 降级。
- MCP/Node 工具不要默认打进主安装包，使用受控的工具目录和 manifest。
- Windows 首发需优先解决代码签名、WebView2 检测/安装、杀毒软件误报和长路径；macOS 需处理 notarization；Linux 提供 AppImage 或发行版包。

### 9.2 更新

- 应用、Python server、协议 schema、插件和模型资源分别记录版本。
- 更新前备份 `data/`，更新后执行 schema migration 和完整性检查；失败可回滚到上一个应用版本。
- 客户端与 server 进行 protocol version negotiation，至少支持前后一个小版本。
- 保留 `--rebuild-index`、`--recompile` 之类恢复命令，并在设置页提供图形化入口。

### 9.3 数据目录

将源码目录与运行数据彻底分离：

```text
AppData/SecondPerson/
  config/       配置和加密凭据引用
  data/         Markdown、SQLite、会话事实链
  workspaces/   默认工作区（可选）
  models/       Embedding/本地模型（可选）
  logs/         轮转日志和诊断包
  plugins/      已安装插件
  updates/      下载中的更新包
```

现有 `data/` 作为迁移输入，首次启动时复制而非移动，完成校验后再切换活动目录。

## 10. 分阶段实施路线

### Phase 0：协议和安全基线（1-2 周）

- 固化 `Session/Turn/Step/Item/Event` schema。
- 为现有 SSE 增加事件序号、request/turn 关联和终态幂等测试。
- 把工具权限、工作区和审批状态写入事件流。
- 补充跨平台路径、命令和进程树测试。

**出口标准：** 不启动桌面壳也能用协议测试客户端完整完成一次代码任务并恢复中断轮次。

### Phase 1：Tauri 壳 + Python sidecar（3-5 周）

- 保留 Vue 页面，接入 Tauri 2。
- Rust Supervisor 启动 Python server、Embedding worker 和 MCP 子进程。
- 解决单实例、托盘、关闭、日志、端口/UDS、崩溃重启和数据目录。
- 打出 Windows 安装包，完成从源码运行到安装包的数据迁移。

**出口标准：** 用户无需 Python/Node 即可安装、启动、聊天、查看记忆和执行一次受控代码任务。

### Phase 2：本地 app-server 和编程工作台（4-8 周）

- 引入双向 JSON-RPC，HTTP/SSE 退化为兼容层。
- 新增文件树、搜索、diff、补丁预览、终端输出、测试结果和审批 UI。
- 所有长任务支持取消、恢复、后台运行和事件回放。
- MCP、Provider、插件管理统一到宿主生命周期。

**出口标准：** 完成“读取项目 → 修改 → 测试 → 查看 diff → 接受/撤销”的闭环，断线恢复不丢状态。

### 架构闸门：Phase 2 结束时必须重新决策

不要预先承诺一定迁移或一定不迁移。先在真实项目和三种目标平台上建立基线，再使用同一套脚本持续测量：

| 指标 | 建议目标（可按首发平台调整） | 不达标时的动作 |
| --- | --- | --- |
| 冷启动（不含模型下载） | P95 ≤ 5 秒 | 优先优化 Supervisor、导入和索引初始化 |
| 空闲内存 | P95 ≤ 350 MB（不含 Embedding 模型） | 将常驻 worker 改为按需启动，评估 Rust 执行器 |
| 崩溃恢复 | 10 秒内恢复窗口和会话，零孤儿进程 | 收紧 Supervisor 和进程树回收，必要时下沉 Rust |
| 断线恢复 | 事件序号连续，无重复终态 | 修复协议/事件日志，不以 UI 临时状态兜底 |
| 代码任务成功率 | 固定基准项目回归无下降 | 优先修复工具和上下文，不直接换语言 |
| 安全审计 | 高危问题为 0，权限拒绝可重放 | 把高权限执行器迁入 Rust 或独立沙箱 |
| 发布维护 | 三平台构建、签名、回滚全自动 | 拆分组件版本，减少 sidecar 变更面 |

这些数值是启动门槛而非宣传指标；第一次测量后应记录真实基线、硬件和样本，再决定是否调整阈值。闸门的目的，是把“长期维护成本”变成可观测的工程事实。

### Phase 3：执行器和高风险组件原生化（按收益选择，6-12 周）

- Rust 实现 process/PTY、进程树、资源限制、路径策略和平台沙箱。
- Python 通过稳定协议调用 Rust 执行器，不再直接掌握所有宿主权限。
- 对频繁使用的索引、文件监控和 token 计量做性能 profiling 后再迁移。

**出口标准：** 高风险工具可在平台级权限边界内运行，主 Agent 崩溃不会带走桌面壳或遗留子进程。

### Phase 4：插件生态和远程控制（后续）

- 参考 DeepSeek Harness 的 capability seam，开放受限插件 SDK。
- 参考 OpenClaw Gateway，支持第二个客户端（CLI/移动或远程 Web）。
- 仅在真实插件需求出现后再决定是否把 Agent loop 迁移到 TypeScript 或 Rust。

## 11. 验收指标

### 产品指标

- 全新 Windows 机器安装后无需开发环境即可完成首次对话。
- 首次启动、选择模型、选择项目、首次代码任务均有可恢复状态。
- 代码任务能展示计划、工具调用、文件变更、命令输出、测试结论和最终 diff。
- 关闭并重启应用后，历史会话、记忆和未完成任务状态可恢复或明确标记失败。

### 工程指标

- Tauri Host、Python server、前端和协议 schema 可独立测试和发布。
- 协议未知事件向后兼容；事件队列有界，过载可重试。
- Windows/macOS/Linux 至少各有一条打包和启动 CI。
- 关键工具的权限、超时、取消、凭证脱敏、路径逃逸和进程回收有自动化测试。
- `data/` 备份可在新版本中重建 SQLite 索引，升级失败可回滚。

## 12. 最终建议（修订）

采用“两阶段目标”而不是一次性押注：

1. **现在落地：** Tauri 2 + Vue 3 + Python sidecar + 版本化本地 app-server。Rust 负责桌面宿主，Python 继续承载现有 Agent 和记忆业务，TypeScript 负责 UI 和协议客户端。
2. **长期收敛：** 保持同一套协议和事件日志，逐步把 Rust Host/执行器、权限、PTY、文件和 Git 能力做成唯一高权限入口；Python 降为可替换 worker。只有 profiling 证明有收益时，才迁移 Agent loop、索引或其他业务模块。

这条路线同时吸收三个参考项目的长处：

- 采用 Codex 的核心/UI/协议分离和可恢复事件模型；
- 采用 DeepSeek Harness 的能力接缝、Host/Client 分离和插件生命周期；
- 采用 OpenClaw 的本地 Gateway 思路，为 UI、CLI、IM 和未来远程客户端提供统一控制平面。

不建议当前就做“全量 Rust 重写”或“全量 Node/TypeScript 重写”，也不建议把 Python sidecar 的 FastAPI 路由当成永久产品契约。Phase 2 结束时应设置一次架构闸门，基于内存占用、启动时间、崩溃恢复、跨平台打包耗时、权限审计结果和半年内的功能变更数量决定迁移范围。这样既能尽快得到可安装客户端，也能避免把迁移期的双运行时方案固化成长期负担。
