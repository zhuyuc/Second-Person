# 自动压缩架构方案（v7）

> 记录：把 `AGENT_MAX_STEPS = 8` 硬切换成 **token 压力驱动的自动压缩** 那一次的关键决策。参照 dsh-compaction-basic 架构改造。

## 一、缘起

改造前：
- `AGENT_MAX_STEPS = 8` 硬编码——聊天+偶尔调工具时代的定值
- 触顶后输出 `"任务已达到最大执行步骤，以下是已完成的结果。"` 的钝面文案
- 会话内**无任何**自动压缩：`agent/compression.py::Compressor` 类定义完备但**无调用点**，`SessionStore.save_summary` 仅存储 API
- `sessions.last_compressed_message_id` 水位字段从未被推进过

现象：项目会话首次问"了解一下这个项目"，模型探索到第 8 步还在读文件（README/pyproject/docs/…），第 9 步才准备综合回答→被硬顶截断→用户看到钝面文案。

## 二、目标

对齐 dsh 的 agentic 探索能力：模型可自然跑 20-30+ 步深度探索，压力由自动压缩管控而非 step 数。

## 三、关键决策

### D1：token 压力驱动，不再依赖 step 数

**改造**：
- `AGENT_MAX_STEPS: 8 → 64`（保留作为"防死循环兜底"，不再是"正常路径截断"）
- 每 step 前置钩子做 token 压力检查，超阈值触发压缩
- 压缩后 messages 复用会话原 system + tools 作前缀（provider KV cache 命中）

**对齐**：dsh-compaction-basic 用 `agent/pre-step` 事件钩子做同事。

### D2：混合度量（anchor + delta）

**候选**：
- (A) 纯 tiktoken 估算——±10% 误差累计漂移
- (B) 纯 provider 精确报——pre-step 时刻没有当轮数字
- (C) 混合：**上一 step 结束的 provider 精确 usage 作 anchor**，本 step 只对 delta（新增 messages）用 tiktoken 估算

**选 C**（对齐 dsh `token-meter/index.ts:29-40` 的注释）。

理由：
- 累计误差不发散——每次 anchor 更新对齐真实数字，误差只累在当轮新增 delta 上
- cache 感知：anchor 保留 `cache_read_tokens`，压力判据用 `uncached_tokens`（`total - cache_read`）而非 `total`，避免"cache 命中还触发压缩"的浪费
- 冷启动降级：无 anchor 时纯估算，保证首次 pre-step 也能判断

**实现**：`agent/token_meter.py::TokenMeter`
- `measure(session_id, messages, system, tools) → TokenMeasurement`（含 `total_tokens` / `uncached_tokens` / `source` / `anchor`）
- `commit_anchor(session_id, messages, usage, system)` —— 每 step 结束由 turn_runtime 调
- Anchor 失效判据：system_hash 变、message_count 缩短、tail_hash 变

### D3：8 段摘要格式（对齐 dsh COMPACTION_INSTRUCTION）

保留 SP 现有 `compress_system.md` 五段结构不动（其他消费者兼容），CompactionEngine 用 **新** prompt：

`agent/prompts/compact_instruction.md`：8 段 markdown（主要请求与意图 / 关键技术概念 / 文件与代码 / 错误与修复 / 待办事项 / 当前工作 / 下一步 / 关键上下文）

`agent/prompts/compact_preamble.md`：CHECKPOINT_PREAMBLE + `<compacted-summary>` 标签，落盘 summary 被这个包裹

### D4：阈值 / 保留比例默认

对齐 dsh 默认：
```python
COMPACTION_THRESHOLD_RATIO = 0.8     # 用满 80% 上下文窗口时触发
COMPACTION_RETAIN_RATIO = 0.2        # 尾部保留 20% 的 tokens
COMPACTION_MAX_RETRIES = 1           # 一次压完仍超阈值最多再压 1 次
```

均可 config 覆盖（`compaction_threshold_ratio` 等）。

### D5：区间选择——tool 对配对不可劈开

`_select_range`：
1. 从尾部倒着累加 tokens 直到 ≥ retain_tokens
2. 检查分界点前面是否是"tool 调用对"中间：assistant 有 N 个 tool_calls 必须紧跟 N 个 role=tool 响应
3. 若在中间——`keep_from` 往前退到成对边界之外

对齐 dsh `region.ts::toolPairingBalancedBefore`。

### D6：压缩后 anchor 失效

压缩改变了 history 结构（前面被 summary 替换），旧 anchor 的 message_count / tail_hash 都不再匹配。压缩成功后 `TokenMeter.drop_anchor(session_id)` 主动清理。下一 step 走冷启动全量估算，直到下一次 `commit_anchor` 建立新 anchor。

### D7：触发点选择

**候选**：`pre-step` vs `post-step`。

**选 pre-step**（对齐 dsh `agent/pre-step` 事件）：
- pre-step 触发时 prompt 已就绪，压缩后可以立刻 rebuild 本 step 的 prompt
- post-step 触发意味着"下一 step 才生效"，模型在本 step 已经用了满 context
- Pre-step 唯一顾虑：多一层"压缩失败→fallback"路径复杂度，但可控

`step >= 2` 才检查——step 1 无累积压力。

### D8：触顶文案不再是钝面报错

`AGENT_MAX_STEPS` 触顶时：
- 如果 `content_parts` 非空（模型至少产出了内容）→ 拼接 + 提示"以上是基于已收集信息给出的部分结果"
- 否则 → 给"任务粒度过大，建议拆分子问题或新开会话"的可操作建议

## 四、Anchor 失效判定的三个信号

| 信号 | 触发原因 | 处理 |
|---|---|---|
| `system_hash` 变 | SOUL 更新、tool_prompts 版本升级 | 冷启动重估 |
| `message_count` 缩短 | 压缩/删除/切换分支 | 冷启动重估 |
| `tail_hash` 变 | 尾部消息被编辑/重生成 | 冷启动重估 |

冷启动重估**只影响一 step**，下 step commit_anchor 又建立新 anchor。

## 五、KV cache 命中收益

改造前后对比：

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 首轮 pre-step 度量 | 无（不度量） | 全量估算（~ms 级） |
| 后续 pre-step 度量 | 无 | anchor + delta（~ms 级） |
| 压缩摘要请求 | 无 | 复用会话 system+tools+span 作前缀，末尾追加 instruction |
| KV cache 命中率 | 触顶前 100% / 触顶就废 | 探索期持续命中，压缩仅一次 miss（末尾 instruction） |
| 用户可见触顶 | 常见（8 步撞线） | 罕见（64 步 + 自动压缩） |

## 六、可选后续（未在本次实现）

### E1：手动 /compact 命令
- API: `POST /chat/session/{sid}/compact` → `compaction_engine.compact_now()`
- 前端 chip 菜单加"立即压缩"
- `compact_now` 目前是 `compact_if_needed(trigger="manual")` 的复用，仍受阈值影响；未来可改为真正强制

### E2：overflow recovery
- LLM adapter 层把 provider 的 `context_window_exceeded` 映射到统一异常
- turn_runtime catch → 强制压缩 → retry 一次
- 保险机制，触发条件极稀有（阈值 0.8 已经离窗口边界很远）

### E3：token_meter 后端化
- 当前 anchor 存在进程内 dict，重启丢失
- 未来可持久化到 `session_token_anchor` 表，重启不重置
- 收益：跨进程/多机部署时保持 anchor 一致
